# PRD v0.1: WarmDiet Growth Bot

## 1. 产品概述

`WarmDiet Growth Bot` 是三餐管家开源项目的推广运营中台。它将开源仓库、线上 Demo、产品截图、宣传视频、行业热点和平台特性组合成每日可执行的内容分发流水线，帮助 `xrunda/warmdiet-platform` 获得持续曝光、真实 star、试点线索和社区反馈。

第一阶段目标不是全自动发帖，而是建立稳定的半自动内容生产和发布流程。系统每天生成 10 条跨平台内容草稿，支持人工审核、素材匹配、发布包导出和效果复盘。

## 2. 背景

三餐管家已经完成开源：

- GitHub 仓库：`xrunda/warmdiet-platform`
- 在线 Demo：医院端和家属端均可体验
- 宣传视频：90 秒竖屏短视频
- 开源策略：open-core，基础产品开源，Enterprise / AI Core 闭源

项目需要持续获取关注，但医疗健康项目不能用粗暴营销方式。增长系统必须兼顾：

- 项目真实价值表达
- 社区信任
- 医疗健康合规
- 多平台内容差异
- 自动化效率
- 人工审核把关

## 3. 目标

### 3.1 业务目标

- 让 WarmDiet 每天获得稳定曝光。
- 促进 GitHub star 真实增长。
- 吸引医院、医生、投资人、开发者和养老行业从业者体验 Demo。
- 建立可复用的内容运营工作流。
- 为后续 Enterprise / AI Core 商业化积累线索和内容资产。

### 3.2 产品目标

- 每天自动抓取热点和项目动态。
- 每天生成 10 条内容计划。
- 为 X、小红书、抖音、视频号、快手生成平台化草稿。
- 支持图片、视频、纯文本三类素材。
- 支持人工审核后发布。
- 记录发布状态和平台数据。
- 逐步接入自动发布能力。

### 3.3 非目标

第一阶段不做：

- 不做买 star、刷量、批量账号矩阵。
- 不做绕过平台风控的强自动发布。
- 不做医疗诊断或治疗建议内容。
- 不接真实患者数据。
- 不把平台密钥、Cookie 或账号信息提交到仓库。

## 4. 用户和角色

| 角色 | 需求 |
| --- | --- |
| 项目负责人 | 看到每日内容计划，确认方向，决定是否发布 |
| Codex 指挥官 | 生成策略、拆任务、审核输出、调度流水线 |
| Claude / 其他 Agent | 按 Issue 实现模块、修复缺陷、补测试 |
| Copilot | 在 PR 内做代码建议和初步 Review |
| 内容审核者 | 审核医疗健康表述、热点借势风险、平台风格 |
| 目标受众 | 医院、医生、投资人、开发者、养老照护相关人群 |

## 5. 核心使用场景

### 5.1 每日半自动内容生产

1. 系统抓取当天热点。
2. 系统读取 WarmDiet 项目状态。
3. 生成 10 条选题。
4. 为不同平台生成文案。
5. 匹配项目截图、视频或封面素材。
6. 输出审核稿。
7. 人工确认、修改或驳回。
8. 生成发布包。

### 5.2 平台发布

第一阶段：

- X：支持 API 自动发布或手动发布包。
- 小红书：生成图文笔记发布包。
- 抖音：生成短视频标题、文案、话题、封面建议。
- 视频号：生成更稳重的行业向文案。
- 快手：生成更直接、生活化的短视频文案。

第二阶段：

- 对可开放 API 的平台接入自动发布。
- 对不稳定平台使用 Browser 半自动填充，人工点击发布。

### 5.3 晚间复盘

1. 读取当天发布记录。
2. 人工或半自动录入平台数据。
3. 分析表现好的选题、平台、素材。
4. 生成第二天内容建议。
5. 更新内容策略。

## 6. 内容策略

每日 10 条内容建议比例：

| 类型 | 数量 | 说明 |
| --- | --- | --- |
| 产品功能 | 2 | 医院端、家属端、授权、Demo |
| 热点结合 | 2 | 养老、医疗 AI、慢病管理、数据授权 |
| 技术开源 | 2 | React、Cloudflare、open-core、工程实现 |
| 视频推广 | 1 | 90 秒视频或短切片 |
| GitHub 动态 | 1 | star、issue、release、开源进展 |
| 产品思考 | 1 | 院外随诊、家属照护、患者授权 |
| 互动问题 | 1 | 向医生、开发者、照护者提问 |

## 7. 平台差异

| 平台 | 内容风格 | 自动化策略 |
| --- | --- | --- |
| X | 技术、开源、产品思考、英文/中文短帖 | 优先 API 自动化 |
| 小红书 | 图文、照护故事、家属视角、截图卡片 | 先发布包，后 Browser 半自动 |
| 抖音 | 短视频、强钩子、快速解释 | 先视频包，后半自动 |
| 视频号 | 行业可信、医疗管理、创业进展 | 先发布包，后半自动 |
| 快手 | 生活化、直接、照护场景 | 先发布包，后半自动 |

## 8. 功能需求

### 8.1 项目状态采集

输入：

- GitHub README
- GitHub star / fork / issue / release
- Demo URL
- 宣传视频路径
- 项目截图路径

输出：

- `data/project-state/yyyy-mm-dd.json`

### 8.2 热点采集

输入：

- 新闻源
- 技术社区
- X / GitHub Trending
- 医疗 AI、养老、慢病、数据合规关键词

输出：

- `data/trends/yyyy-mm-dd.json`

要求：

- 每条热点记录来源、标题、摘要、链接、时间、可信度。
- 标记是否适合 WarmDiet 借势。
- 敏感医疗事件默认不借势。

### 8.3 选题生成

输入：

- `data/trends/yyyy-mm-dd.json`
- `data/project-state/yyyy-mm-dd.json`
- 内容策略配置

输出：

- `content/calendar/yyyy-mm-dd.json`

要求：

- 每天 10 条。
- 每条包含目标平台、受众、核心观点、素材类型、风险等级。
- 避免重复昨天内容。

### 8.4 文案生成

输入：

- 内容日历
- 平台风格配置

输出：

- `content/drafts/yyyy-mm-dd/*.md`

要求：

- 同一选题可生成多平台版本。
- 每条文案必须有合规自检结果。
- 医疗健康表述必须保守。

### 8.5 素材管理

输入：

- 项目截图
- 宣传视频
- 封面模板
- 生成图片

输出：

- `assets/packaged/yyyy-mm-dd/...`

要求：

- 根据平台输出推荐尺寸。
- 第一阶段可以只生成素材需求和引用路径。
- 后续接入 Remotion / Figma / 图片生成。

### 8.6 审核流

输出：

- `content/review/yyyy-mm-dd.md`

要求：

- 人能快速看到 10 条内容。
- 每条有 Approve / Edit / Reject 状态。
- 默认不自动发布未审核内容。

### 8.7 发布适配器

第一阶段接口：

```text
publish:manual
publish:x
publish:xiaohongshu:package
publish:douyin:package
publish:wechat-video:package
publish:kuaishou:package
```

要求：

- 发布动作必须写入日志。
- 失败必须可重试。
- 自动发布必须可关闭。

### 8.8 数据复盘

输入：

- 发布记录
- 平台数据手工录入或自动采集
- GitHub star 增量

输出：

- `content/reviews/yyyy-mm-dd.md`
- `data/metrics/yyyy-mm-dd.json`

## 10. MVP 范围

MVP 必须实现：

- 本地 TypeScript 项目骨架。
- 配置文件示例。
- 项目状态采集的 mock / local 版本。
- 热点数据的 mock / 手动导入版本。
- 生成每日 10 条内容计划。
- 生成多平台草稿 Markdown。
- 生成审核汇总文件。
- 生成手动发布包。
- 本地发布记录和复盘模板。
- 基础测试。

MVP 可以不实现：

- 真实 X API 发布。
- 国内平台自动化。
- 自动生成图片或视频。
- 自动读取所有平台指标。

## 11. 成功指标

### 11.1 产品指标

- 每天能生成 10 条可审核内容。
- 每条内容都有平台、受众、素材和合规检查。
- 每天可产出审核汇总。
- 发布记录可追踪。

### 11.2 业务指标

- GitHub star 每周稳定增长。
- Demo 访问有增长。
- 至少每周获得一次真实反馈。
- 至少每周沉淀一篇可复用内容资产。

## 12. 风险

| 风险 | 应对 |
| --- | --- |
| 内容像 spam | 限制每日链接比例，提高观点密度 |
| 医疗健康表达过界 | 增加合规检查和禁用词规则 |
| 国内平台风控 | 优先半自动，人工确认发布 |
| 热点借势翻车 | 敏感事件默认不借势 |
| Codex 额度不足 | Codex 做指挥和验收，Claude 做编码 |
| 代码项目失控 | GitHub Issue + PR + Review 流程 |

## 13. 待澄清问题

1. 第一个运营账号是中文为主、英文为主，还是中英双语？
2. 每天 10 条是总量 10 条，还是每个平台各 10 条？
3. X 是否已经有 Developer API 权限？
4. 国内平台账号是否已有登录态和创作者后台权限？
5. 是否允许使用项目视频切片作为每日素材？
6. 是否希望把每日草稿同步到飞书、Notion 或表格？
7. 审核人只有项目负责人，还是后续会有运营同学？
8. `growth-bot` 代码是否也要随主仓库公开，还是后续迁移到私有仓库？

## 14. v0.1 默认决策

在用户进一步确认前，MVP 按以下默认决策推进：

| 问题 | v0.1 默认决策 |
| --- | --- |
| 运营语言 | 中文优先，X 可额外生成英文版本 |
| 每日 10 条定义 | 全平台总量 10 条，不是每个平台各 10 条 |
| X API | 第一阶段不要求真实 API 权限，先生成发布包 |
| 国内平台 | 第一阶段只生成发布包，不做自动登录和发布 |
| 视频切片 | 允许使用项目宣传视频切片作为素材来源 |
| 草稿同步 | 先落本地 Markdown/JSON，不接飞书、Notion、表格 |
| 审核人 | 默认项目负责人单人审核 |
| 代码可见性 | 暂随主仓库提交，但密钥、Cookie、私有运营数据必须进入 `.gitignore` |

这些默认决策只用于启动 MVP，不代表最终产品约束。
